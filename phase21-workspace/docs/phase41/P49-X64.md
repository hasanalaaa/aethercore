## ITEM 2 — Gate 5 on x64, against this build

The full lifecycle, never yet run on x64 against a current build.

Restore point first, verified by enumeration. Then: install with `/l*v`, the
16 files plus hashes, service state / account / SID, install-dir ACLs, the
dev-binary sweep, the four verbs with timings, `engineLabel`, uninstall, the
**fourteen-check survivor sweep**, and reinstall.

EXPECTED: **zero survivors on all fourteen.** Any survivor is a finding recorded
with its exact path — never deleted by hand and called a pass. Note P47 raised
`DBT-P47-002` about what `UNINSTALL.txt` claims survives; check the sweep against
the corrected text.

**Pipe DACL** must be byte-identical to:

    O:<service SID> G:SY D:P(A;;FA;;;<service SID>)(A;;FR;;;AU)(A;;DC;;;AU)

`(A;;0x12008b;;;AU)` is the SAME DACL — `FR|DC = 0x120089|0x2 = 0x12008b`. **Not
drift.** Read it with:

    [System.IO.File]::Open('\\.\pipe\AetherCore.Maintenance.v7',
      [IO.FileMode]::Open,[IO.FileAccess]::Read,[IO.FileShare]::ReadWrite)

then `.GetAccessControl().Sddl`. Service SID must be **UNRESTRICTED**.
`engineLabel` must report `localModel` **against the running service** —
`aetherctl self-check --load-model` returning exit 7 is correct by design and is
not the proof.

## ITEM 4 — DBT-P42-011, the bias, re-measured

Recorded: cpu +7.47 and +4.09 points, disk latency 3.47x, three readings all the
same direction. ARM64 shows no such bias. macOS is inconclusive.

**Those numbers predate P45's field-boundary fix. Re-measure on the current build
before explaining anything.** Run the product and `Get-Counter` in the same
window, under real sustained load, at least three rounds. Report every reading
beside the host's, with the delta in points and as a ratio.

EXPECTED: the bias reproduces. **If it does not, that is the finding — say so and
stop.** Do not hunt a cause for something that is gone.

If it does reproduce, establish the mechanism with `file:line`, or state plainly
that it is not established and name the measurement that would settle it.
Candidates, none privileged: the sampling window versus the host counter's
window; the denominator; the basis-point conversion (`DBT-P42-002` was exactly
that class); and whether the product and the host read the *same* counter object —
`\Processor Information(_Total)\` and `\Processor(_Total)\` differ on modern CPUs.

**Do not fix it.** A cadence or denominator change alters every reading on the
qualified platform and needs its own review.

## ITEM 5 — the VC++ runtime guard, verified WITHOUT breaking this machine

P48 proved `DBT-P41-001` on the VM by removing the redistributable: install
refused with 1603 naming the runtime, and the binaries died `0xC0000135
STATUS_DLL_NOT_FOUND`. The guard works.

**Do not remove the VC++ redistributable from this machine.** It is the owner's
real working computer, other software depends on that runtime, and the behaviour
is already proven on ARM64. The value of repeating the removal here does not
justify breaking a daily-use machine that has no snapshots.

Verify the x64 side without removing anything:

- the `Launch` condition is authored in the x64 MSI and names the runtime —
  read it out of the built MSI's tables, not the source
- the Burn chain lists `VCRedist` first, from the manifest (Item 1 covers this)
- the x64 binaries' actual imports: `llvm-objdump -p` over all six installed
  binaries. EXPECTED, per §48: five of six import `VCRUNTIME140.dll`, the service
  also imports `MSVCP140.dll`, and `VCRUNTIME140_1.dll` is x64-only
- what the machine currently has installed, with version

That is enough to say the guard is correctly authored on x64. State explicitly
that the refusal itself is proven on ARM64 and inferred here — do not claim it as
measured on x64.
