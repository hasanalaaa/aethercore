# P59 ITEM 3 — is `OMEGA-RB-001` reachable?

**Yes. It ran to completion on 2026-09-12 at 08:43:39Z, in 62 seconds, and
nobody kept the output.**

`OMEGA-RB-001` has blocked release since Phase 19 — thirty-nine phases — and the
owner register has carried "a dependency freeze from a trusted workstation" for
all of them. The brief asked whether the closure is possible. It is not only
possible; it already happens, on a schedule, and the artefacts are destroyed
with the runner.

The freeze was **not** run for this phase. Everything below is read from the
script, from the repository, or from a CI run that had already happened.

### One portability defect, found by reading and not executed

Lines 9–12 build the output paths with a **backslash**:

```powershell
$lockBaseline = Join-Path $Root 'release\dependency-locks.sha256'
```

PowerShell's `Join-Path` does not normalise separators, and `\` is a legal
character in a POSIX filename. On macOS or Linux `-Refresh` would therefore
write three files literally named `release\dependency-locks.sha256`,
`release\dependency-manifests.sha256` and `release\dependency-freeze.json` in
the workspace root, not into `release/`. This is a code reading — `pwsh` is not
installed here, so it was **not executed** and is stated as a belief, not a
measurement. `Hash-Line` at `:17` already does `-replace '\\','/'`, so the
baseline *contents* are portable; only the output paths are not.

## 3.B — what is "the trusted dependency-freeze workstation"?

**It is not defined anywhere in this repository. That is the finding.**

The phrase appears in twenty-odd places — `freeze-dependencies.ps1:39, 44, 83`,
`omega-evidence.py:469`, `release/dependency-freeze.blocker.json:8`,
`docs/RELEASE_SUPPLY_CHAIN.md:33`, `PHASE_9_VALIDATION_SUMMARY.md:36`,
`ZENITH_ISSUE_LEDGER.md`, `ZENITH_REMAINING_RISKS.md`, `docs/LEDGER.md` §3 row 5
and the P36 session context — and **not one of them says what makes a
workstation trusted.** No criteria, no register of approved machines, no
attestation, no key, no owner.

Two attributes were ever attached to it, both in prose, both in passing:

- **Windows** — `docs/RELEASE_SUPPLY_CHAIN.md:17`, "On a trusted connected
  Windows workstation"; `AetherCore-Phase19-Source/README.md:95`, "A trusted
  Windows dependency-freeze workstation".
- **connected** — the same line.

That is the whole specification. A barrier whose precondition was never written
down cannot be met deliberately, which is the most economical explanation for
thirty-nine phases of no attempt.

## 3.D — what the owner would actually have to do

### The barrier is inherited language, not a real constraint

`.github/workflows/windows-installer.yml:109-110` runs
**`./scripts/freeze-dependencies.ps1 -Refresh`** — not `-VerifyOnly` — on every
dispatch, on a GitHub-hosted `windows-latest` runner.

```

  step 10 of 12  "Create candidate dependency evidence"   success

  08:42:37Z  Resolving dependency lockfiles from pinned manifests...
  08:42:xx   Updating crates.io index
  08:42:xx   Locking 559 packages to latest Rust 1.97 compatible versions
  08:43:xx   Already up to date            (pnpm --lockfile-only)
  08:43:39Z  Phase 9 dependency graph frozen. Review and commit lockfiles
             plus all release/dependency-* baseline files together.
```

**Sixty-two seconds, on a connected Windows machine, green, today.** The three
missing files were written and the blocker was deleted. Then the runner was torn
down, and `windows-installer.yml` uploads only
`phase21-workspace/out/release/**/*.exe`, so the freeze set went with it.

The freeze has been succeeding for as long as that workflow has existed. What
has never happened is **keeping the result**.

### The graph review has nothing in it right now

Measured on this Mac, writing nothing:

```
$ cargo update --dry-run --workspace
    Locking 0 packages to latest Rust 1.97 compatible versions
note: pass `--verbose` to see 11 unchanged dependencies behind latest
warning: not updating lockfile due to dry run
```

`cargo generate-lockfile` re-resolves to the newest semver-compatible versions,
which is what `cargo update` does — and today that moves **zero packages**. The
eleven `Adding … (available: …)` lines in the CI log are the same eleven held
back by their own version requirements. pnpm reported `Already up to date`.

So a refresh performed now would leave `Cargo.lock` and `pnpm-lock.yaml` at the
same resolution they already have, and the commit would be **three new files
plus the deletion of the blocker**. Whether `Cargo.lock`'s bytes come back
identical was not measured, only its resolution.

### P58's objection does not transfer, and should not be carried forward again

P58 (and `docs/LEDGER.md` §3 row 5) argued that producing the freeze set on a
developer machine would inherit `DBT-P55-007` — signature validation being inert
off CI. **It would not.** `DBT-P55-007` is about `dotnet tool restore` and
NuGet's `signatureValidationMode` / `trustedSigners`, exercised when the pinned
WiX tool is restored. `-Refresh` runs `cargo generate-lockfile` and
`pnpm install --lockfile-only`; neither performs a NuGet restore, so that
control is not in this path at all.

The real risks of refreshing on an untrusted machine are different ones — a
poisoned local cargo/npm cache, or a registry the machine resolves differently —
and neither applies to a clean GitHub-hosted runner.

### Concretely, in order

1. **Capture what CI already produces.** Add
   `phase21-workspace/release/dependency-locks.sha256`,
   `dependency-manifests.sha256` and `dependency-freeze.json` to
   `windows-installer.yml`'s `upload-artifact` paths, dispatch it once, and
   download the three files. One workflow edit and one run.
2. **Review the graph** — the owner's decision, not a session's, and today it is
   a graph that has not moved: `cargo update --dry-run` locks 0 packages.
3. **Commit the three files and delete `release/dependency-freeze.blocker.json`**
   in one commit. `Cargo.lock` and `pnpm-lock.yaml` are already committed and do
   not change.
4. **Rerun `ci.yml`.** Its `windows` job reaches step 2 of 16 for the first time,
   and the remaining fifteen gates get to say something.

Alternatively, step 1 is `./scripts/freeze-dependencies.ps1 -Refresh` on the
owner's own Windows PC, which is Windows and connected — the only two attributes
the repository ever attached to "trusted". Not from this Mac: `pwsh` is absent,
and the backslash paths in `:9-12` would misname the output.

**What this does not settle.** Whether the owner is willing to sign off on the
current dependency graph is a risk acceptance and stays his. What P59 removes is
the belief that he *cannot* — the mechanism works, on a machine that exists,
and it took a minute.
